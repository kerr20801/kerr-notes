# 幫朋友的 AI 問卷工具做滲透測試：沒挖到注入漏洞，挖到了兩個「AI 功能」自己的坑

寫於 2026-07-27

---

朋友做了一個小工具：輸入一句話當主題,AI 幫你生一份問卷,產生連結分享出去讓人填。

拿到帳號、朋友本人在群組裡口頭授權後,順手花半小時做了一輪 App 層測試。範圍很保守:不碰底層架構,不動別人的資料,只測自己帳號能碰到的東西。

結果沒挖到傳統意義的漏洞,反而挖到兩個更有意思的坑——都出在「AI 功能」這條路徑上,不在傳統 Web 安全那條路徑上。

---

## 先講測了什麼、沒問題的部分

- **登入 SQLi**:帳號欄位塞 `'`、`' OR '1'='1`,回應都是乾淨的 401 + 正常錯誤訊息,沒有 SQL 錯誤外洩,沒有繞過。看起來是 ORM/參數化查詢,沒問題。
- **Stored XSS**:標題、說明、題目欄位塞 `"><script>alert(1)</script>`、`<img src=x onerror=...>`,不管是列表頁、管理頁還是公開填寫頁,輸出全部正確做了 HTML entity escape。範本引擎有把這件事做對。
- **管理連結 IDOR**:管理連結是「以 token 當憑證」的設計(不是 session-based 權限判斷)。試了空 token、亂猜 token,都是乾淨的 404,不會洩漏問卷是否存在或內容。這個設計本身是合理的。

傳統攻擊面(注入、XSS、越權)這幾塊,基本功做得扎實。

---

## 真正的坑:AI 產生內容那條路徑

### 坑一:非同步 job 卡死,卻沒人告訴你

AI 產問卷的流程是丟一個背景工作,前端用 htmx 每 2 秒 poll 一次進度。

實測:進度卡在「正在擬定問卷標題…」超過一分鐘不動——但標題其實已經寫進資料庫了,只是**題目生成那一步沒有跑完**。

問題是,一份「0 題」的問卷,系統的行為是:
- 公開填寫連結 `/polls/{id}` → 404
- 結果頁 `/polls/{id}/results` → 404
- 連問卷擁有者自己登入都看不到,完全不知道哪裡出錯

我手動幫這份問卷補一題進去,兩個 404 立刻變 200。證實了問題就是「0 題狀態」本身沒被當一回事——不是路由壞了,是**非同步任務沒有失敗處理,半成品資料留在系統裡,而下游完全沒有針對「不完整資源」設計對應行為**。

使用者體驗上等於:點了 AI 產生 → 卡住 → 就算它其實部分成功了,分享連結也是壞的,而且沒有任何錯誤訊息告訴你為什麼。

### 坑二:AI 生出來的中文,經過一手變亂碼

拿正常手動輸入的問卷標題比對,完全沒有這個問題——問題只出在「AI 生成文字」這條路徑,人工輸入那條路徑是乾淨的。八成是呼叫 LLM API 拿回應那段,中間經過某個預設 Latin-1 的函式庫或 header 沒設對。

---

## 為什麼這兩個坑比 SQLi 更值得寫下來

傳統注入類漏洞,現在框架預設值基本上都幫你擋掉了(參數化查詢、自動 escape 是主流框架的預設行為,不是加分項)。

但「串 AI API」這件事是新拼進系統的一塊,還沒有像 SQLi 防禦那樣變成肌肉記憶:

- 呼叫外部 LLM API 是非同步、會失敗、會慢——但很多實作只想著 happy path,沒設計「job 死在一半」該怎麼收尾
- LLM 回應是純文字,經手的每一層(API client → 業務邏輯 → DB driver → 模板引擎)只要有一層對編碼做錯誤假設,中文就死給你看

這類坑不會被掃描器抓到,因為它們不是「安全漏洞」,是「AI 功能整合的工程債」。但對使用者來說,體驗上的傷害不比一個低風險漏洞小——你的核心功能(AI 產問卷)實際上是壞的,而且完全靜默。
