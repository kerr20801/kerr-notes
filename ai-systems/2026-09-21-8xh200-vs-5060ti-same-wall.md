# 8×H200 跟我家一張 5060 Ti，撞到同一堵牆

> 寫於 2026-09-21

---

同事丟了一篇轉貼到 GitHub 的 FB 貼文給我，內容是某團隊用 8 張 H200（TP8、BF16）跑 Qwen3.8-Flash-Next，做了 950 多次壓力測試。結論一句話：**顯存還有空間，不代表能再塞使用者進去，真正卡住的是每個人分到的速度。**

看完的第一反應不是「這篇準不準」，是「這不就是我上個月才踩過的坑」。

---

## 一、他們說的數字

先把貼文的主張列出來，這些都是**他們單方面說的**，我沒有原始 log 可以核對：

- 系統總顯存 1,018 GiB，KV cache 吃掉 613.8 GiB（約 560 萬個 token 的量）
- 每個請求固定要吃 6,670 個 token 的「linear attention 遞迴狀態」，不管輸入多長都一樣
- Prefill 階段在 200K context 下維持 26.8K tok/s，長序列只掉 15%
- 短對話（2K~8K context）可以撐 145~256 個併發使用者
- 32K 的 RAG 情境掉到只剩 27 人（理論值 142，**崩了 81%**）
- 128K~256K 超長 context 只剩 9 個人能用（**崩 55~77%**）
- 整體吞吐量在併發拉高後停在「44→56 tok/s」——但這個數字是整個系統的總量，還是每個人分到的量，貼文沒講清楚，這是我沒辦法確認的地方

貼文自己也承認：沒有公開測試腳本、沒有原始 log、沒寫用哪個推理框架的哪個版本，是「社群貼文，非同行審查」。

---

## 二、這正是我上個月寫的那篇文章講的事

我 9/1 那篇〈換一顆模型，換到的不只是回答品質——還有你能開幾條連線〉裡算過一件事：**KV cache 大小跟併發數是同一份記憶體預算的兩種花法，模型權重反而是固定成本，不是變數。** 那次是拿自己一張 RTX 5060 Ti 16GB，用 gemma4:26b 實測出來的。

規模差了幾百倍（8 張企業級 H200 vs 家用一張消費卡），但物理限制長得一模一樣：不是機器夠大就能繞過去，是併發數、context 長度、KV 精度三者綁在同一份預算裡，加一個就要從別的地方扣。這篇貼文只是在完全不同的規模、完全不相干的團隊手上，重新驗證了一次同一條規律。

**這是讓我相信這篇貼文核心論點的原因，不是因為它的具體數字，是因為它跟我自己動手量出來的東西方向一致。**

---

## 三、但具體數字不能直接引用

方向可信，不代表每個數字都可信。這篇貼文缺的正好是我自己一直在用的判準：**只信真實任務域的頭對頭實測，不信沒有可重現方法的 benchmark。**

具體卡在哪：

- 「44→56 tok/s」沒說是總吞吐量還是單人速度，兩種解讀差幾十倍，這種模糊在嚴謹的 benchmark 裡不該出現
- 沒有測試腳本、沒有框架版本，代表沒辦法排除是某個推理框架（vLLM？SGLang？TensorRT-LLM？）當下某個版本的特有問題，而不是模型或硬體的根本限制
- 手上這份是別人轉貼到 GitHub 的二手 markdown，不是原始貼文，連結都沒附，沒辦法回頭查證

有一點倒是值得記著、之後找機會驗證：貼文說 Qwen3.8-Flash-Next 是 linear attention，每個請求的狀態大小固定、不隨輸入長度增加。如果是真的，這跟我自己測過的 gemma4（sliding-window attention，KV 幾乎不隨 context 拉長暴增，65535 ctx 只要約 2GB，而 full attention 的 Qwen3.8:27b 同樣設定要 24~48GB）是同一種設計精神，只是用不同數學方式達到類似效果。但這只是貼文單方面的說法，沒有第一手數據佐證，先記著，不當定論。

---

## 收尾

這類二手轉貼的 benchmark 貼文，判斷方式不是「信」或「不信」二選一，是拆開來看：**結論**如果跟你自己動手驗過的東西方向一致，可以信；**具體數字**沒有可重現的方法論，就只能當參考，不能直接引用。這篇貼文剛好兩邊都占——結論可信，數字不能照抄。
