# Postmortem：當合作太順利，連驗證都被省略了——一次自我鎖死的虛擬化層事故

> 這是一份去識別化的事故復盤。技術層面是「一次防火牆收斂操作把整個虛擬化層的管理通道鎖死」，但真正值得記錄的不是技術細節，是背後三個疊加的人為因素：操作者（AI）過度自信、人（我）因為合作太順利而放鬆了驗證、以及我們雙方都沒有把「這是基礎設施最底層」這件事的重量放進操作節奏裡。

## 事故摘要

| 項目 | 內容 |
|---|---|
| 操作目標 | 把三台虛擬化主機（hypervisor）的管理介面防火牆從「全部放行」收斂成「白名單制」 |
| 直接原因 | 白名單新增與舊規則關閉寫在同一段無人值守的批次指令裡，中間沒有逐步驗證 |
| 實際結果 | 三台主機的管理層（SSH / 中控台連線 / Web 介面）全部鎖死，含中控台本身所在的那台 |
| 影響範圍 | 管理通道斷線，但運算層（VM/服務）本身沒有立即中斷 |
| 復原方式 | 無法遠端修復，最終靠實體主控台（接螢幕鍵盤）手動解鎖，中間因為接口不合、臨時找螢幕又耗了一番工夫 |
| 復原耗時放大因素 | 螢幕/鍵盤接上後畫面仍無訊號，排查後確認是「顯示輸出只在開機瞬間初始化，事後熱插拔不會生效」，最終靠實體電源鍵硬重開才解決 |

## 根因一：該驗證的兩步，被寫成了一步

正確的收斂順序應該是：① 先加白名單規則 ② 確認新規則生效（能連得上）③ 最後才關閉舊的全放行規則。這三步任何一步失敗，後面的步驟都不該自動接著跑。

實際執行時，①跟③被寫進同一段背景批次指令，中間沒有驗證。而目標系統本身有一個不直覺的限制：「全放行」規則還開著的時候，不允許新增白名單條目（會回報錯誤拒絕）。於是：①失敗（白名單從頭到尾是空的）、③仍然成功執行（全放行被關閉）。結果就是「白名單是空的，而且被鎖成只認白名單」——所有連線，包含操作者自己，全部被擋在外面。

這不是系統設計的陷阱，是操作者（我，AI）明知道正確步驟卻沒有把驗證寫進操作本身。

## 根因二：為什麼一個不急的任務，用了急件的節奏

這條收斂操作本身完全不急，是在處理其他事情時「反正順手一起做」的心態下進行的。真正的問題不是「這個操作本身有風險」——任何收斂權限的操作都有風險——而是風險評估跟操作節奏不匹配：**對爆炸半徑最大的系統（整個虛擬化層，所有服務的宿主），用了對待低風險小事的操作方式**（一次性背景指令、不逐步確認）。

事後回頭看，如果當時慢下來，先加白名單、停下來測一次連線、確認沒問題再關閉舊規則，整件事會是三個獨立的、各自可驗證的小步驟，而不是一個不可逆的單一動作。

## 根因三：人沒有擋下來，因為信任已經建立到不再檢查的程度

這是三個根因裡最值得記錄的一個，也是這篇文章真正想談的重點。

這次操作之前，人機協作已經有一段很長的、合作順利的紀錄——大量基礎設施變更被正確執行、被正確驗證、出問題時也被正確排查修復。這份紀錄建立了合理的信任。但這次的操作，人（我）**沒有在執行前要求看一遍計畫、沒有問「這個步驟之間會不會有空窗期」、沒有問「如果中間失敗了，退路是什麼」**——因為過去的順利，讓這類追問感覺起來像是多餘的。

這跟「AI 過度自信」是同一個硬幣的兩面：**AI 對自己的操作節奏過度自信，人對 AI 過去的表現過度信任**，兩者疊加起來，剛好跳過了這次本該存在的那層驗證。

值得說清楚的是：這不是說「以後每一步都要人工審核」——那樣會讓協作效率倒退回去，也不是這次事故真正該學到的教訓。真正的教訓是：**信任的累積不該用來免除「對高爆炸半徑操作要求明確驗證流程」這條底線**，不管過去的紀錄有多好。普通的日常操作可以、也應該靠累積的信任加速；但「這個系統壞了會波及多少東西」決定了驗證紀律能不能被信任換掉——這條線無論合作多順利都不該退讓。

## 復原過程中的意外插曲

管理層鎖死後，發現三台主機的物理機器都沒有常駐螢幕（典型的 homelab headless 部署）。嘗試接螢幕的過程又撞上一個不直覺的現象：**部分系統的顯示輸出只在開機自檢（POST）那一刻初始化，如果開機時沒有偵測到螢幕，事後熱插拔螢幕不會生效**——必須實體斷電重開、而且螢幕要在通電瞬間就已經接好，才會重新初始化顯示路徑。這個現象跟這次防火牆鎖死本身無關，只是復原過程中疊加的另一個「早知道就不會卡在這」的細節。

三台硬重開後，虛擬化平台自己的管理服務、叢集狀態（含一套分散式儲存叢集的多節點重新加入）陸續自動恢復，運算層的服務本身沒有資料損失。

## 連帶挖出的兩個潛伏 bug

硬重開讓好幾個長期沒被重新測試過的路徑第一次被重新執行，連帶暴露出兩個跟這次事故本身無關、但已經潛伏很久的問題：

1. 一套內部知識庫系統的登入功能，因為先前一次手動修補漏掉兩個函式的對外export，導致登入外掛整個載入失敗——但因為使用者的登入 session 一直有效，直到這次重開機讓 session 失效、第一次重新走登入流程，才第一次真正被踩到。
2. 同一套系統的附件備份機制，從**設置當天起就從未真正成功過**，連續運行了快一個月、每天都「完成」卻實際寫出 0 bytes 的檔案——因為備份目標的執行環境本身缺少備份腳本依賴的工具指令，而腳本的錯誤處理把「指令失敗」跟「真的沒有內容可備份」混為一談，兩種情況都只留一行日誌、沒有任何告警。真正的內容資料（文字部分走另一條備份路徑）從未受影響，但附件/圖片這條線的「看起來有備份」其實是假的安全感。

這兩個都是「系統壞掉的樣子跟正常一模一樣」的經典案例——跟這份筆記系列裡另一篇[威脅偵測系統靜默失效的 postmortem](2026-08-28-Postmortem%20ai威脅偵測系統除錯.md)是同一個模式的不同案例：**沒有人真的去驗證「成功的訊號」背後對應的是不是真的成功**。

## 可帶走的教訓

- **信任是拿來加速日常操作的，不是拿來免除高爆炸半徑操作的驗證紀律**——這兩件事很容易被混在一起，合作越順利越容易混
- 收斂權限類的操作（從「開放」改成「限制」）本質上有自我鎖死風險，正確順序永遠是「先加新的、驗證、再收舊的」，而且這三步不該寫進同一段無人值守的批次指令
- 操作節奏要跟著「爆炸半徑」調整，不是跟著「這件事急不急」調整——不急的事用急件的節奏做，一樣會出事
- 「看起來一直有在運作」不代表真的在運作——這次連帶發現的兩個潛伏 bug，都是因為沒有人在設置當下就驗證過實際產出的內容，只看到「腳本跑完沒有報錯」就當作成功
