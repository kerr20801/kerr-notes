# 決策模型來了，但你該關心的不是它有多快

> 寫於 2026-10-05。三週內 TypeSafe、OpenAI、AWS、Cloudflare、Perplexity 全部推出「決策模型」，新聞一面倒在比延遲。
>
> 但我自己跑了兩年的交易判斷系統，踩過的坑跟延遲一點關係都沒有。這篇講的是：**這類模型真正解決了什麼、沒解決什麼，以及那個沒人強調的欄位才是重點。**

---

## 結論先說

1. 決策模型確實解決了一個真實的工程問題：**不再需要「生成文字 → 正則解析」這條脆弱的鏈**
2. 但它**不會讓錯的判斷變對**。格式穩定跟判斷準確是兩件事
3. 真正值得關注的是**校準過的機率輸出**，而這點在多數報導裡只是表格裡的一個數字
4. 現在就跳進去沒有好處——這個領域三週大，**連獨立第三方測試都還沒有**

---

## 這是什麼：跟 LLM 的根本差異

一般 LLM 做的事是「逐 token 生成文字」。你要它做判斷，它得先把判斷寫成一段話，你再從那段話裡把答案挖出來。

決策模型不一樣：**你先定義好允許的選項，模型讀完輸入之後，直接對每個選項算分數，回傳機率分布。它根本不會產生文字。**

省掉逐步生成那段，就是它快的原因。

用途很明確——AI agent 工作流裡的三種決策點：

- **routing**：這個請求該走哪條路徑
- **gating**：這個工具該不該執行
- **scoring**：這個案件多緊急

## 目前的玩家

| 模型 | 廠商 | 參數 | 開源 | 價格/百萬 token | 中位延遲 |
|------|------|------|------|----------------|---------|
| Jev 1.13 | TypeSafe | 未公開 | ❌ | $0.042 | 524.1 ms |
| pplx-decider-v1-27b | Perplexity | 27B | ✅ | $0.04 | — |
| Clef | Cloudflare | 27B | Apache 2.0 | $0.24 | 209.3 ms |
| Clef-flash | Cloudflare | 9B | Apache 2.0 | $0.09 | **38.8 ms** |
| Strands Decider 2B | AWS | **2B** | Apache 2.0 | 自託管免費 | 106~150 ms |

幾個技術細節：

- **Clef / Clef-flash** 基礎是 Qwen3.8-27B 與 Qwen3.5-9B，上下文 64K，**可處理圖片**，API 相容 Jev
- **Strands Decider 2B** 拿 Qwen3.5-2B 改的：移除次詞預測元件、換成「指標」評分元件（只多 100 萬參數）、LoRA rank-16。JevBench 準確率 72%、Brier score 0.35

起點是 TypeSafe 9 月中推出的 Jev（創辦人 Diogo Almeida 是前 OpenAI 員工）。三週內 OpenAI 出 Decisions API、AWS 開源 Strands Decider、Cloudflare 開源 Clef——**這個速度本身就說明大廠認定這是個真需求。**

## 我踩過的坑：格式脆弱是真的會死人

我自己有一套跑在真實資金上的台股判斷系統，裡面有個模組會讓 LLM 給出離散判決（NOW / WAIT / PASS、ADD / HOLD），然後用正則把判決撈出來存進資料庫。

**這條鏈斷過兩次，而且兩次都是靜默失敗。**

第一次：模型輸出格式從

```
【推薦】2454 聯發科 — 理由 / 偏多
```

變成

```
【推薦】
  - **6933 AMAX-KY** — 理由 / 偏多
```

正則是 `r'【推薦】(.+)'`，而 `.` 不吃換行。**結果抓到空字串，連續 7 個交易日一筆都沒進資料庫。**

更糟的是失敗方式：`if not picks: return` ——**靜默 return，log 裡什麼都沒有**。等我發現的時候，已經少了一週的追蹤資料。

第二次：換 LLM 供應商之後，新模型愛加 markdown 粗體，`**6933 AMAX-KY**` 這種格式又把正則打斷了。**同一個坑，換個姿勢再踩一次。**

**這正是決策模型要解決的問題。** 判決根本不經過文字，就沒有解析可言，上面兩個 bug 在架構上不可能發生。

---

## 但格式修好，不代表判斷會變對

這才是我想講的重點。

我那套系統裡還有另一個模組：三個 LLM 組成的「陪審團」，對個股投票。做了幾百筆之後我回頭驗證：

**命中率 33.3%，p = 0.0002。**

注意那個 p 值——**它不是「沒效果」，是統計上顯著地在扣分**。三個 LLM 一起投票的結果，比丟銅板還糟，而且糟得很穩定。

如果我當初把那個陪審團換成決策模型，會發生什麼事？

**我會得到一組格式穩定、延遲更低、再也不會解析失敗的錯誤判斷。**

這就是我覺得目前討論歪掉的地方：**大家在比 38.8ms vs 524ms，但如果判斷本身是錯的，快 13 倍只是讓你更快拿到錯的答案。**

---

## 真正該看的欄位：Brier score

AWS 公布 Strands Decider 2B 的數字時，除了 72% 準確率，還給了一個 **Brier score 0.35**。

多數報導把這個數字跟準確率並列帶過，但**這兩個東西測的根本不是同一件事**：

- **準確率**：答對幾題
- **Brier score**：你說「我有 80% 把握」的那些題目，是不是真的對了 80%

這叫**校準（calibration）**。一個模型可以準確率很高但校準很爛——它每題都說「我 99% 確定」，然後對 72%。

**為什麼這對我特別有感？**

我系統裡最高信心等級的訊號叫 NOW。截至 2026-10-05 的累計驗證結果：

| 訊號等級 | 筆數 | 命中率 | 平均報酬 |
|---------|------|--------|---------|
| NOW（最高信心）| 234 | 39.7% | **-1.10%** |
| FLAG | 17,941 | 46.5% | +0.40% |
| WATCH | 9,478 | 42.6% | +0.22% |
| 全體基準 | 28,464 | — | +0.32% |

**標示「現在就做」的最高信心訊號，是全部裡面表現最差的，落後基準 1.42 個百分點。**

問題出在哪？**NOW 是一個標籤，不是一個機率。** 它沒有告訴我「這次有多確定」，所以我無法做「只在信心 > 0.8 時才行動」這種分層，也無法回頭驗證「信心 0.5~0.6 那群的歷史表現如何」。

**決策模型原生輸出機率分布，這是它比較少被強調、但對我最有價值的一點。**

## 驗證狀況：別急著信廠商的 benchmark

這點要特別講，因為目前的數字品質參差不齊：

- **只有 Cloudflare 發布完整對比表**，而且是用自己的測試集
- **Perplexity 宣稱的 85.71%，只出現在一則 X 貼文**，沒有可驗證的方法學
- **AWS 的 72% 沒有跟 Jev 直接對比**
- **至今沒有任何獨立機構做過同質化測試**

而且 iThome 在報導 Clef 時講了一句很誠實的話：

> 各模型在不同測試的準確度並非全面由 Clef 領先，例如 Jev 在部分測試仍取得較高成績。

換句話說：**Cloudflare 速度大勝（快 13 倍），但準確度互有勝負。**

這在任何新技術的早期都一樣——**廠商會挑對自己有利的維度公布**。延遲是最容易做漂亮、也最容易比較的數字，所以大家都在比延遲。但對多數應用來說，**延遲從 524ms 降到 38ms 根本不會改變任何商業結果**；準確率差 5% 才會。

## 那到底該不該用

我的判斷分兩段：

### 值得做的

**如果你的痛點是「生成文字再解析」這條鏈**，那決策模型方向完全正確——我自己就被這條鏈咬過兩次。

但在換模型之前，有個**成本低得多的中間解**：**把現有 LLM 改成結構化輸出（JSON mode / function calling）**。這一樣能消滅正則解析，不用換架構、不用新基礎設施，今天就能做。

**先做這個，確認痛點真的解決了，再評估要不要換模型。**

### 先別急的

**如果你的痛點是「判斷不夠準」，換決策模型解決不了。**

通用決策模型不會知道你的領域——它不知道台股外資籌碼怎麼讀，就像它不知道你客服系統裡哪類工單真的緊急。真要讓它變準，**得用你自己的歷史資料微調**，而那需要：

1. 一份乾淨、帶結果標註的訓練集
2. 一個對照組，用來證明新方法真的比舊的好

Cloudflare 已經在賣微調服務、也規畫自助平台，方向是對的。**但你得先有資料。**

我的情況算幸運：26,849 筆帶驗證結果的歷史訊號，本身就是現成的訓練集。但即使如此，我也不打算現在動——**因為在「有對照組證明它比較好」之前，換掉一個已知表現的系統，只是把不確定性換個位置放。**

---

## 給正在評估的人的三個問題

1. **你的失敗是格式問題還是判斷問題？** 格式問題有更便宜的解法（結構化輸出）；判斷問題換模型不會好
2. **你有沒有辦法驗證新方法比較好？** 沒有對照組就別換，不然你只是換了一個你更不熟的黑盒子
3. **你在意的是延遲還是準確率？** 如果你的系統是每 30 分鐘跑一次的排程，38ms 跟 524ms 對你沒有任何差別

---

## 一句話總結

**決策模型是個真實的類別，解決了一個真實的工程問題。但它解決的是「怎麼把答案拿出來」，不是「答案對不對」——而後者才是多數系統真正卡住的地方。**
