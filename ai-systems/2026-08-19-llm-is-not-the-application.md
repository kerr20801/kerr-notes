# 「本地 AI 太笨」很多時候只是「沒有應用架構」的另一種說法

寫於 2026-08-19

---

最近看到一部分享本地 AI 部署踩坑經驗的內容，作者換了好幾顆模型都沒解決問題，最後放棄本地路線、回頭用付費雲端模型。過程本身沒什麼特別，但裡面三個具體卡住的地方，剛好完整示範了一個我一直想寫清楚的觀念：**很多人說「本地 AI 太笨」，其實是把「模型」跟「AI 應用」當成同一件事。**

## 三個具體案例

**案例一：套件內建的搜尋工具在特定語系介面下，會傳送錯誤的 API 參數名稱，導致請求直接被拒。** 作者的解法是乾脆關掉這個內建工具。

這其實是最基礎的維運問題——上游套件的參數命名跟後端 API 對不上，架一層反向代理或寫幾行 middleware 做參數重寫（parameter rewrite）就解決了，跟模型能力完全無關。這種攔截層在正式的網路架構裡到處都是：WAF 規則、API gateway 的請求轉換、reverse proxy 的 header 改寫，都是同一件事的不同應用場景。作者選擇關掉工具，等於是把一個五分鐘的架構問題，活生生變成一個功能缺陷。

**案例二：要求模型輸出結構化資料（例如檔案格式、連結）時，模型會「亂來」——把純文字檔案的副檔名寫成別的格式，或編出根本不存在的連結。作者的應對方式是在 system prompt 裡用強調語氣警告模型不要這樣做。**

這是把「跟模型聊天」和「呼叫函式」這兩件事混在一起了。要模型精準輸出符合特定格式的資料，不是靠自然語言勸說，是在推論框架這一層直接**約束輸出格式**（structured output / JSON schema constrained decoding）——模型在解碼階段就被限制只能生成合法的 token 序列，不合法的路徑根本不存在，不是「模型比較聽話」，是從機制上就沒有亂來的空間。這是本地推論框架（不管是 vLLM 還是其他）行之有年的標準能力，用文字警告去解決這個問題，效果本來就不穩定，換再強的模型也一樣。

**案例三：某些通訊平台的 API 沒辦法直接傳檔案，或是呼叫指令列工具傳檔時參數帶錯，作者卡在這些協定細節裡出不來。**

這是最典型的「把後端工程的活丟給語言模型做」。一個健康的架構分工應該是：**模型只負責產出意圖跟內容**（「我需要一份文件，內容是這些」），實際產生檔案、處理通訊協定、呼叫平台 API 傳送，全部是後端程式碼的責任，跟模型完全脫鉤。讓模型自己去搞懂某個通訊平台的檔案傳輸協定，本身就是架構分工錯了，跟模型聰不聰明無關。

## 三個案例背後其實是同一個誤解

這三個問題有個共同點：**都不是「模型不夠聰明」，是「這件事本來就不該丟給模型做」。**

而這正好指出一個更根本的誤解：**很多人把 LLM 當成「AI」的全部，而不是「AI 應用裡的一個元件」。** 換模型沒用，是因為壞掉的從來不是模型能力，是缺了模型以外的整層東西——路由、驗證、協定處理、格式約束、錯誤重試。這些不是模型的工作，是應用工程的工作。

而且這個誤解不分本地或雲端。**雲端 AI 產品好用，也不是因為雲端的模型比較神。** 檢索系統、意圖分類器、guardrail、工具呼叫的 schema 約束、多層驗證——那些產品用起來體感聰明，是因為整套應用工程做足了，模型呼叫只是其中一個環節。差別只在雲端廠商把這層基礎設施包好藏在後面，讓人誤以為「魔法」全部來自那顆模型；本地部署因為要自己動手把這層搭出來，缺口就直接曝出來，逼你面對現實。

換句話說：**如果你不懂怎麼設計 AI 應用（路由、驗證、任務分解、協定分層），不管接的是本地模型還是最貴的雲端模型，都會撞上同一堵牆。** 模型只是引擎，讓車子能開的是傳動系統、煞車、方向盤——那些才是「應用工程」，不是「AI」的一部分而已，是決定 AI 能不能真正發揮的全部。

## 一個可以驗證的判準

下次遇到「AI 做不到 X」的抱怨，可以先問一句：**這件事本來就應該讓模型做嗎？** 如果答案是「這其實是個協定問題／格式問題／路由問題」，那換模型永遠沒用——先把應用架構補齊，模型能力才有意義。這個判準本地雲端通用，跟預算大小無關。
