# 「換個終端機，Claude Code 生產力差 13 倍」——那個數字是除出來的

> 寫於 2026-10-02

---

看到一則貼文，說很多人裝了 Claude Code 卻還在 CMD 上跑，像買了跑車只在土路上開。接著給數字：CMD 只提升 30%、整合 VS Code 200%、再上 WSL2 加 tmux 衝到 400%。所以工具用得對不對，差 13 倍。

400 除以 30 等於 13.3。

那個「13 倍」不是量出來的，是把自己編的兩個數字相除得到的。

---

數字假只是表面，更麻煩的是那個軸本身選錯了。

就 Claude Code 來說，終端機的影響比想像中小。它不依賴系統的 POSIX 工具鏈——讀檔、搜尋這些是內建工具，不是 shell 出去呼叫 `grep` 跟 `find`。「Windows 上沒有像樣的 grep 所以很痛」對一般開發成立，在這裡大部分不成立。剩下的差異是終端機的 ANSI 跟 Unicode 渲染，那是好不好看。

WSL2 那格還會反過來。要管的是那台 Windows 本身的話，原生環境是直接碰到目標，WSL2 中間多一層檔案系統邊界，跨層存取慢、權限語意不一樣。**它是你做 Linux 的事情時才是升級，做 Windows 的事情時是降級。** tmux 同理，它解決的是 SSH 斷線後 session 還在——人坐在那台桌機前面，沒這個問題要解。

---

那真正的變因是什麼。

我第一個想到的是「關聯度」：這台 Claude Code 摸得到什麼。有沒有接 MCP、有沒有 SSH key 到各節點、有沒有一份寫清楚環境長相的文件。

這個答案比終端機好，但還是不對。**關聯只是天花板，不是產出。**

---

舉今天的例子。我要在 ELK 上做一套 DNS 行為偵測，本來打算直接開始寫。真正改變結果的是一句「先盤一下哪些 index 真的可用」。

盤下去才發現，原始 log 文字存在 `event.original`，而所有 index 的 `message` 欄位填充率都是 0%。照原計畫動手的話，偵測器會建在一個永遠空的欄位上，每天準時執行、永遠回報沒有異常——而「沒有異常」正好也是它正常運作時的樣子。

那不是工具的功勞，是決定「先確認再動手」的功勞。

同一天我還自己造了一個假數字：量「多少暴力破解事件被漏掉」查出 355 萬筆，很驚人，差點寫進結論。抽三筆原文來看才發現查詢用的是全文比對、會把片語拆成 OR，中的全是 `failed to get namespaces` 這種東西。改成精確比對後是 0 筆。抓到它的不是更好的工具，是「拿到很有感的數字先抽樣看原文」這個習慣。

---

最乾淨的反例是我自己。前陣子人在國外，用手機 SSH 回家裡處理基礎設施。沒有 VS Code、沒有 WSL2、終端機也是將就的，按那篇的標準是土路極致。但它能跑，因為另一端什麼都接好了，而且我知道要先查什麼。

反過來，一台 WSL2 加 tmux 加 VS Code 全部配到滿分、什麼都沒接、操作的人也不知道要驗證什麼的機器，上面的 Claude Code 只能幫忙寫寫單檔程式。

環境滿分，操作是零，乘起來還是零。

---

那篇最後問：你會讓你的工程師花一個下午來做這種升級嗎。

這句問錯了兩次。真正有差的東西一個下午做不完——把系統一條條接起來要幾個月，養成「先確認再動手」「拿到數字先抽樣」要更久。而且它不是主管能代做的；環境可以統一規範，但什麼時候該放手、什麼時候該盯，只能實際在用的人自己練。

把它講成一個下午的環境升級，等於把唯一真正困難的部分，講成了最簡單的那部分。
