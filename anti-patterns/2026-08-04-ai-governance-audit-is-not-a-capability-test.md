# AI 治理稽核（ISO 42001 / NIST CSF）電的不是能力，是沒寫成文件

> **結論先說**：技術團隊常常以為稽核在考「有沒有做到」，結果被電得莫名其妙。真相是——稽核在考「有沒有寫成政策」。你系統裡跑得很好的機制，如果只存在 code 跟 runbook 裡，沒有一份治理文件說「我們的政策是 X，落地方式是 Y」，稽核眼裡就是零分。

---

## 一個常見的落差

團隊裡技術能力很強，AI 相關的防護機制堆得又深又細：權限分層、異常偵測、人工複核關卡、回饋修正迴圈，樣樣都有，而且是真的在生產環境跑，不是 PPT 上的願景。

結果找第三方認證機構（ISO 42001、NIST CSF 這類）來對，卻被電得莫名其妙——對方問「你們的 AI 風險治理政策文件在哪」，答不出來，因為根本沒有這份文件，只有一堆會動的系統。

這不是能力不夠，是**兩種東西被混為一談**：

- 「我們有做」＝ 系統裡有這個機制，跑得動
- 「我們符合治理要求」＝ 有一份文件寫「這是我們的政策」，並且系統跟文件對得起來

前者是工程問題，後者是文件問題。稽核機構檢查的是後者。

---

## 稽核機構在看什麼

拿常見的幾個類別對照：

| 稽核類別 | 技術團隊常有的東西 | 稽核要的東西 |
|---------|-------------------|-------------|
| 存取控制 | RBAC、角色分層、特權操作白名單，程式碼裡寫死 | 一份「存取控制政策」文件，說明角色定義、審核週期、誰核准 |
| 異常偵測 | 一堆 watchdog、ML 監控腳本，24/7 在跑 | 一份「監控與偵測策略」，說明涵蓋範圍、通報流程、責任人 |
| 變更管理 | Merge Request 審核流程，有人 review 才會上線 | 一份「變更管理政策」，寫明誰有權核准、什麼情況要多人審核 |
| AI 輸出品質 | Prompt 裡寫死「不確定就說不知道」、有人工評分回饋機制 | 一份「AI 系統可靠性/人工監督政策」，說明怎麼量測、怎麼處理失準 |
| 資料治理 | 個案判斷「這份資料能不能進 AI」，看情況決定 | 一份「資料分類與 AI 使用政策」，寫明分級標準跟允許用途 |
| 第三方模型 | 換模型前會做效果比較、有回退機制 | 一份「供應商/模型風險評估紀錄」，每次引入新模型的正式評估 |

看規律：左邊都是「系統裡真的有」，右邊都是「寫成正式文件、可以拿給人看」。技術團隊在左邊投入的心力遠遠超過右邊，因為左邊直接影響系統穩不穩、安不安全；右邊在日常工作裡不影響任何事，直到稽核那天才被想起來。

---

## 為什麼會有這個落差

因為寫程式碼的回饋是即時的——機制做對了，事故變少、告警變準，馬上有感。寫治理文件的回饋是滯後的——文件寫不寫，平常系統照樣跑，只有稽核那天才會被戳破。

在資源有限的情況下，人自然會投入有即時回饋的事，滯後回饋的事往後排，一排就是排到稽核前一週才發現自己什麼都沒有。

這不是團隊懶，是**兩種工作的回饋週期差太多**，不特別提醒自己，永遠會偏向即時回饋的那一邊。

---

## 補這個落差不是重做，是翻譯

好消息是：真正的落差通常不是「能力不夠要重建」，是「實務沒有翻譯成文件」。

```
現有落差 ≠ 缺技術
現有落差 = 缺一層翻譯：
    「code 裡的行為」 → 「文件裡的政策聲明」
```

具體做法：把現有機制倒著寫回去。不是先寫政策再叫工程照做（那是理想化的正向流程，實務上很少團隊真的這樣運作），是先看系統實際在做什麼，再補一份文件說「這是我們的政策，這是我們怎麼落地的證據」。

這件事的成本，比從零開始建一套治理框架低一個數量級——因為要治理的東西早就存在，只是沒人把它寫下來過。

---

## 一句話版本

> 稽核不會因為你系統很強而放過你，也不會因為你文件寫得漂亮但系統是假的而讓你過。它要兩邊對得起來——但多數技術團隊只做了其中一邊，而且是稽核不看的那一邊。
