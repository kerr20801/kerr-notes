## 重點

- 機房防火牆的一個對外 IP 被打了約 15 分鐘，流量只有線路頻寬的兩成，機房的自動防護卻把整個 IP 黑洞了 **17 小時**。
- 這個 IP 沒有對外服務，所以沒有服務中斷；但曾經經由這條線出網的流量受到連帶影響。
- **防火牆日誌看不出這次攻擊**。連線筆數在平常範圍內，證據只有「機房通報」加「介面流量曲線」。
- 只用「流量大小」做告警會一直誤報；回測 78 天後，唯一乾淨的特徵是「**衝高後歸零**」。
- 我們自己的告警在「解除」判斷上少了連續確認，單次小流量就誤報「已解除」。

## 發生了什麼

某個下午，機房通知：防火牆其中一個 WAN 介面的 IP 出現異常流量，已自動攔阻（只放行來源在國內的流量，也就是黑洞）。

我們這邊的觀察（監控系統每 5 分鐘取樣一次）：

| 時間 | 現象 |
|---|---|
| T−2.5 小時起 | 往該 IP 的連線日誌筆數緩慢上升，但仍在平常範圍內 |
| T | 該介面入站流量由平時約 30 Mbps 衝到約 210 Mbps，約為 1 Gbps 線路的兩成 |
| T+15 分鐘 | 入站流量降到接近 0 |
| T+17 小時 | 機房解除攔阻，流量在約 50 分鐘內回升到平時水準 |

機房通報的數字與我們量到的一致（約 216 Mbps、2 萬 pps），所以沒有「我們只看到一部分」的問題。

## 學到的六件事

### 1. 小流量不代表不會被黑洞

這次的流量遠低於線路容量，也沒有超過合約頻寬。更特別的是：同一個介面在前幾週曾多次出現同等級（200 Mbps 以上）的突波，從未被攔阻。所以機房的觸發條件**不是單看流量大小**，可能與封包數、來源或攻擊型態有關。這點我們沒有得到機房的答覆，只能列為未知。

**怎麼用**：不要用「流量沒超過容量」推論「不會被防護機制處置」。把「機房防護的觸發條件與範圍」列為要向機房確認的事項。

### 2. 黑洞的副作用比攻擊本身大

黑洞通常是針對**整個目的 IP**。如果被打的 IP 上有對外服務，黑洞會讓部分使用者連不上；即使沒有服務，只要有內部主機經由該介面出網，回程封包也可能被擋。

這次因為被打的 IP 沒有任何服務，影響很小。但同一台防火牆的另一條線上有對外服務，如果被打的是那個 IP，後果會完全不同。

**怎麼用**：監控告警除了「哪條線異常」，要同時列出「這條線上有哪些對外服務」。我們把這個對照從 IP 登記表自動帶進告警訊息。

### 3. 連線日誌不等於流量

我們一開始把「往該 IP 的連線日誌」當成攻擊證據，後來用同一條件和平常 6 天比較（排除自家主機），才發現：

| 每 30 分鐘筆數 | 平常 6 天 | 事件當天下午 |
|---|---|---|
| 全部協定 | 中位 2,029／第 95 百分位 3,835 | 2,081 到 3,647 |
| UDP | 812／2,546 | 532 到 1,295 |
| ICMP | 432／722 | 231 到 505 |

原因：這個 IP 平常就一直被全網掃描，日誌量本來就高；日誌記錄的是「連線」，大量封包若集中在少數連線，筆數不會跟著增加。

**怎麼用**：體積型攻擊的證據要看介面流量（bps、pps），不是日誌筆數。用日誌當證據前，先和同時段的平常值比。

### 4. 日誌裡最大的「攻擊來源」其實是自己人

日誌中來源最多的幾個位址，反查後是**辦公室防火牆自己的對外 IP**，背後是內部主機（容器叢集與使用者電腦）對該 IP 的 UDP 長期連線，每天固定出現，一直被擋下。它們與這次攻擊無關，卻佔了事件時段日誌的約 28%。

**怎麼用**：判讀來源 IP 前，先對照自家的 IP 登記表排除自己人；另外，體積型攻擊的來源 IP 常是偽造的，不能直接當攻擊者資訊，更不要拿去做封鎖或餵進學習資料。

### 5. 只用流量大小做告警，誤報太多

用 5 分鐘資料回測 78 天（兩台防火牆、10 條序列，基線取「過去 7 天同時段 ±1 小時的中位數」）：

| 規則（單次取樣） | 觸發次數 |
|---|---|
| ≥ 3 倍基線且 ≥ 100 Mbps | 221（約每天 3 次） |
| ≥ 4 倍且 ≥ 150 Mbps | 64（約每天 0.8 次） |
| ≥ 5 倍且 ≥ 200 Mbps | 17（約 11 個獨立事件） |

歷史上 200 到 400 Mbps 的突波很常見，多半是正常的大量傳輸。這類規則會一直響，最後被忽略。

### 6. 告警的「進場」與「解除」要對稱

我們原本的告警進場要「連續兩次檢查成立」才通知，用來避免抖動；但新加的「疑似黑洞」告警，解除條件寫成「單次回到基線 20% 以上」。上線當晚，某一格出現約 13 Mbps 的短暫流量（超過基線 20%），就被判成「已解除」，發了解除通知，下一格又掉回接近 0。更糟的是，因為衝高已經超過偵測窗口，規則不會重新偵測，等於**黑洞還在，卻沒人追蹤**。

**怎麼用**：進場和解除用同一套連續確認，並在上線後隔夜看一次實際行為。單元測試和 dry-run 抓不到現場抖動。

## 我們最後採用的偵測規則

唯一乾淨的特徵是「**衝高後歸零**」：

```text
對每個入站介面，每 10 分鐘：
  baseline = 過去 7 天「同時段 ±1 小時」的中位數
  peak     = 最近 90 分鐘內 5 分鐘平均的最大值
  now      = 最近 10 分鐘平均
  若 peak ≥ max(4 × baseline, 150 Mbps)   # 先前有明顯衝高
     且 now ≤ 0.02 × baseline              # 現在幾乎沒流量
     且 衝高發生在「現在這 10 分鐘」之前    # 先升後降
  → 告警「疑似被黑洞」，附上這條線上的對外服務清單

解除：now ≥ 0.2 × baseline，且「連續 2 次檢查」都成立
```

回測：把這條規則掃過全部歷史（約 10 萬個「序列 × 時點」），**只有 1 筆符合，就是這次事件**。

## 回測的限制（請誠實看待）

- **只有 1 個正樣本**。這只能說明「在這份資料裡沒有誤報」，不能證明它抓得到其他型態的攻擊。
- 它只抓「被黑洞」這個型態，**抓不到沒被黑洞的體積型攻擊**，也不會比機房通報更早。
- 回測資料只涵蓋部分介面；基線需要至少 8 天歷史。
- 流量走勢用 5 分鐘平均，真正的尖峰可能更高。
- 我們沒有封包數（pps）資料，所以無法驗證「機房是看 pps 觸發」這個猜測。

## 可以帶走的檢查清單

- [ ] 告警訊息有沒有附「這條線上有哪些對外服務」？
- [ ] 有沒有向機房確認：觸發條件、黑洞範圍、有服務的 IP 能否豁免？
- [ ] 沒有對外服務的 IP，是否關閉不必要的回應（例如 ping）？
- [ ] 判讀日誌來源前，是否排除自家位址？
- [ ] 告警的進場與解除是否對稱（都要連續確認）？
- [ ] 新告警上線後，是否隔夜檢查過實際行為？
- [ ] 體積型攻擊的證據，是否來自流量（bps／pps），而不是日誌筆數？
