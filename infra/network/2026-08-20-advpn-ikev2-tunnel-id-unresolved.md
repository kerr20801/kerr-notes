# 隧道 up、BGP Established、路由也學到了——封包就是過不去

寫於 2026-08-20

---

先講結論：

> **把 ADVPN 的 hub 從 IKEv1 改成 IKEv2 之後，控制平面全部正常，資料平面完全不通。**
> 根因是 hub 學不到各 spoke 的隧道介面 IP，轉發時解析不出該用哪一條 SA。
> 但這不是「IKEv2 有問題」——同一台設備上另一條 IKEv2 dial-up 隧道好好的。
> 真正會爆的是 **「IKEv2 ＋ 一條 phase1 底下多條 SA ＋ 隧道 IP 靠交換學來」** 這個特定組合，
> 三個條件缺任何一個都不會出事。

這篇同時是一份除錯過程的記錄，因為過程中**有三個診斷工具分別給了我看起來合理、但實際上是錯的答案**——那部分可能比結論本身更有用。

---

## 症狀：所有你會去看的地方，全都是綠的

拓樸是一個 hub 對多個 spoke 的 ADVPN，走 iBGP 交換路由。改成 IKEv2 之後：

| 檢查項目 | 狀態 |
|---|---|
| IPsec 隧道 | ✅ up，phase2 也 up |
| BGP 鄰居 | ✅ Established |
| 收到對方路由 | ✅ 學得到，next-hop 正確 |
| 廣播我方路由 | ✅ 對方也收得到 |
| 防火牆政策 | ✅ 放行，且 NAT 已關 |
| 路由表 | ✅ 目標網段有路由，遞迴解析正常 |
| **實際 ping** | ❌ **100% packet loss** |

每一個「該檢查的地方」都正常。這種狀況最難搞，因為沒有任何一個紅燈可以當線索。

---

## 三個騙了我的診斷工具

### 一、封包側錄：顯示「送出去了」，其實沒有

```
diagnose sniffer packet any 'host <遠端主機>' 4
...
Kerr_Lan in   <來源> -> <遠端主機>: icmp: echo request
Advpn    out  <來源> -> <遠端主機>: icmp: echo request     ← 看起來送出去了
```

每一個 echo request 都顯示 `Advpn out`，但沒有任何回應。我當下的結論是：**我方一切正常，問題百分之百在對方**。

**這個結論是錯的。**

`Advpn out` 顯示的是**路由決策把封包交給了那個介面**，不是**封包真的被加密送上線**。這中間還有一步——選擇要用哪一條 IPsec SA——而封包正是死在那一步。側錄看不到這個區別。

### 二、隧道位元組計數器：戳破前一個謊言

真正給出答案的是最笨的方法——打一串 ping，前後各讀一次隧道計數器：

```
Advpn_0 (spoke A): 進 +540 bytes / 出 +0 bytes
Advpn_1 (spoke B): 進 +191 bytes / 出 +52 bytes   ← 這 52 是 BGP keepalive
```

15 個 ICMP（約 1260 bytes）打出去，**隧道的送出計數是 0**。封包從來沒有被加密過。

側錄說送出去了，計數器說沒有。**計數器贏——因為它更難造假**：側錄反映的是軟體流程走到哪，計數器反映的是真的有多少 byte 進了加密引擎。

### 三、Session API 回傳 0 筆：不是「沒有 session」，是「沒給我資料」

中途我想從管理 API 撈連線表來看封包被哪條政策處理，結果回傳 0 筆。差點下結論「連 session 都沒建立」——但再查一次總數也是 0，而設備上明明有幾百條連線。

**API 沒給資料，不是設備沒資料。** 空結果第一個要懷疑的是自己查錯地方，不是「真的沒有」。

---

## 真正給出答案的工具

`diagnose debug flow` 會逐步印出封包的處理決策，包含丟棄原因：

```
find a route: gw-10.255.1.2 via Advpn              ← 路由 OK
Allowed by Policy-17                                ← 政策 OK
enter IPSec interface Advpn, tun_id=0.0.0.0        ← 問題在這
```

**`tun_id=0.0.0.0`**。封包進到 IPsec 介面時，沒有對應到任何一條實際的隧道，然後就消失了。

對照設備上實際的隧道 ID：

```
Advpn_0 → tun_id = 203.0.113.10
Advpn_1 → tun_id = 203.0.113.20
```

設備知道「要送去下一跳 `10.255.1.2`」，但**不知道 `10.255.1.2` 屬於哪一台 spoke**。

再往下一層，看 IKE 層學到了什麼：

```
diagnose vpn ike gateway list

name: Advpn_0
  virtual-interface-addr: local: 10.255.1.1
  virtual-interface-addr: remote: 10.255.1.254     ← 注意

name: Advpn_1
  virtual-interface-addr: local: 10.255.1.1
  virtual-interface-addr: remote: 10.255.1.254     ← 兩條一模一樣
```

兩條隧道都回報對端是**同一個位址**——而那個位址是 hub 自己介面上寫死的 `remote-ip`，**不是從 spoke 學來的**。

**hub 從來沒學到每個 spoke 各自的隧道 IP。** 這就是根因。

---

## 為什麼一般的站對站 S2S 用 IKEv2 完全沒事

這是最值得帶走的一段。差別不在 IKE 版本，在**一條 phase1 底下有幾條 SA**：

| | SA 數量 | 需要選路嗎 |
|---|---|---|
| **一般 S2S**（靜態、點對點） | 1 條 | **不用**。封包交給那個介面，只有一條路可走，不可能選錯 |
| **ADVPN hub**（dial-up） | **N 條**（每個 spoke 一條） | **必須**。要決定「這個封包進哪一條 SA」 |

一般 S2S 之所以怎麼設都能通，是因為**它根本沒有選擇題**。ADVPN hub 才需要「隧道 IP ↔ SA 對應表」這層額外機制，而那層在 IKEv2 下沒有運作。

### 最有說服力的證據：同一台設備上的對照組

這台設備上還有另一條給手機用的 **IKEv2 dial-up** 隧道——一樣是 IKEv2、一樣多個 client、一樣一條 phase1 對多條 SA——**它完全正常**。

差別只有一個設定：

```
手機那條:  set mode-cfg enable     （設備主動配發位址：.1 給筆電、.2 給手機）
ADVPN:     set mode-cfg disable    （各 spoke 自己寫死隧道 IP）
```

**位址是設備自己發出去的，它當然知道哪個位址屬於哪條 SA——對應表天生就有，不需要跟對方交換。**

所以完整的因果是：

> 不是 IKEv2 壞掉，是「**IKEv2 ＋ 多條 SA ＋ 隧道 IP 靠交換學來**」這個組合壞掉。
> 缺任何一個條件都不會出事。

順帶一提，這也指出了「如果堅持要用 IKEv2」的正解：**改用 mode-cfg 讓 hub 配發隧道位址**，繞開那個失效的交換機制。代價是雙方都要改設定、要協調位址範圍，不是幾行指令的事。

## 修法與驗收

比對版控裡「還能用的時候」的設定備份，還原三項（保留期間做的加密強度調整，那部分與本問題無關）：

```
config system interface
    edit "Advpn"
        set remote-ip 10.255.1.254 255.255.255.255   # 遮罩改回 /32
    next
end

config vpn ipsec phase1-interface
    edit "Advpn"
        set ike-version 1
        set net-device enable
    next
end
```

還原後路由表立刻出現關鍵的一條：

```
10.255.1.2/32   connect   dev=Advpn_0     ← IKEv1 的介面 IP 交換機制在運作
```

驗收（**兩項都要看，只看一項會再被騙一次**）：

```
5 packets transmitted, 5 received, 0% packet loss, avg 2.87 ms
隧道計數器: 進 +491 bytes / 出 +472 bytes        ← 故障時這裡是「出 +0」
```

## 我在這次除錯裡犯的四個錯

這些比結論更值得記，因為它們都是可以複製的思考錯誤：

**一、拿文件通則覆蓋現場證據。** 官方文件寫「ADVPN hub 必須 `net-device disable`」，我照著建議改。但這套部署**能動的時候一直是 `enable`**——我沒有先去查它可用時長什麼樣，就把系統改離了已知可用狀態。文件描述的是通則，版控裡的設定備份描述的是**這一套實際能動的樣子**，衝突時後者優先。

**二、推薦了一個五年前就被移除的參數。** 建議設定 `tunnel-search nexthop`，事後才查到該選項**自 v7.0.1 起已移除**。API 讀出來是 `None` 不是「設定漏了」，是「這個東西已經不存在了」。

**三、推薦了一個根本不存在的指令，而且 API 還騙我說成功了。** 建議設定 `exchange-interface-ip`——CLI 直接回 `command parse error`，這個版本沒有這個指令。更糟的是我先用 REST API 試，它回：

```json
{"status": "success", "http_status": 200, "revision_changed": false}
```

**`status: success` 但 `revision_changed: false`。** 讀回來確認，值完全沒變。如果只看 `status` 欄位，會以為改好了然後往錯的方向繼續查。**寫入之後一定要讀回確認，不能相信回應裡的成功欄位。**

**四、根據會騙人的證據下了「百分之百」的斷言。** 就是前面那個側錄的例子。「百分之百在對面」這種話，建立在一個我沒有驗證過其語義的工具輸出上。

四個錯的共同形狀是同一句話：

> **通則不能覆蓋現場證據，而現場證據本身也要先確認它到底在講什麼。**
