# 升了 FortiOS 8.0 才發現想要的功能被硬體排除，還順手挖到一個會自己緩過來的管理服務死鎖 —— 當天就降回 7.6.7

寫於 2026-08-19

---

我升級家用 FortiGate 的動機很單純：8.0 加了內建的 AI 助理功能，想早點摸熟，之後在正式環境要評估升版時能少走彎路。查完文件才發現，這個念頭一開始就注定落空——但我還是升了。這篇記錄接下來發生的事，以及為什麼**升版本身可能比不升更危險**。

## 想要的功能，其實升版前就已經被硬體排除

AI 助理功能的官方文件寫著一個很容易被忽略的硬性條件：**記憶體要大於 2GB**。

我這台設備實測只有 **1919MB**。差了 81MB，不管裝哪個版本的韌體都跑不動——這是硬體規格的天花板，不是「等下個版本修好」可以解決的問題。

理性上這時候該打退堂鼓。但我還是決定升，理由是「反正遲早要熟悉新版架構」。這個決定我事先講清楚了風險（升版過程可能斷線），也做好了回退準備（備份好升版前的設定）。**先講清楚：這篇不是在說「早知道就不升」，是想記錄升版之後實際發生的兩個問題，尤其是第二個——一個我完全沒預期到、目前查不到官方對應說明的管理服務死鎖。**

## 升版之後，兩個問題

### 問題一：VPN 撥入的手機解不到內網主機名

升版前我剛好花了一輪時間把三條 VPN 隧道的加密強度做了調整（這部分不是這篇重點，簡單說：用設備自己的 debug log 時間戳做真實測試，而不是相信文件上的理論排序，測出來橢圆曲線群組整體比傳統 MODP 群組快、也更安全）。

升版之後在其中一條給手機撥入用的隧道上，設了網域後綴推送（讓連上 VPN 的手機打內網短主機名時能自動補上網域），結果解析仍然失敗，但 IP 直連完全正常。

查證後發現：**這個推送機制在舊版韌體上根本沒有被配置過**——不是新版弄壞了舊版能用的東西，而是我從來沒開啟過它。（補充更正：我一開始誤以為這個欄位是新版才有的，實際上舊版的較新修訂版就已經提供，降版之後回頭查證確認欄位仍然存在。這個誤讀不影響結論，只是把原因從「機制不存在」修正為「機制存在但沒啟用」。）另外，舊版還有另一個對應欄位，在官方社群論壇上本來就有「設了會被忽略」的已知回報。換句話說，**這不是回歸（regression），是我第一次踩上一條本來就不太穩的路**。

現場開 debug 想抓包確認，結果連續三輪、合計快 4 分鐘，一次都沒抓到手機端送出任何查詢或連線嘗試——說明我們根本沒有同步測到過一次，連「查了解不到」的階段都還沒到。這條線後來我自己也改了懷疑方向（可能跟撥入用的是哪個 IKE 版本有關，不是韌體版本），先擱置沒繼續深挖。

### 問題二：管理介面的 web 服務會自己卡死，而且會自己緩過來

這個才是意外的重點。

除錯過程中，設備的管理 API 和 GUI 數度完全沒有回應——不是慢，是連續等 15~45 秒都拿不到任何回應。查了才發現：處理管理連線的那個 web daemon，有**兩個 worker process 長期咬死兩顆 CPU 核心**，跑滿 99.9%，管理平面因此完全癱瘓。

強制砍掉那兩個卡死的 process 之後，process 立刻自動重生、CPU 瞬間掉回接近 0%，管理介面恢復正常。

聽起來像是解決了？**這個現象在一個半小時內反覆發作了三次。**而且我一路排除掉了幾個「合理解釋」：

- 不是我除錯操作誘發的——後面兩次發作時我完全沒在跑任何東西，其中一次是我自己在 GUI 上獨立確認連不上，跟我當下的操作完全無關
- 不是官方唯一查得到的近似已知問題——那條記錄講的是另一個特定頁面在流量大時 GUI 沒反應，官方給的 workaround（關掉一個日誌相關設定）試了完全無效，CPU 依然卡在 90%+
- **它會自己緩過來，不一定要人工介入**——第三次卡死之後，我看到管理介面「自己恢復了」，但查開機時間發現**完全沒有歸零**，證實那不是重開機生效，是這個 daemon 自己從死鎖狀態走出來的

這種「會自己卡死、也會自己活過來」的行為，是我目前查文件查不到的一個新版本穩定性問題。它不影響封包轉送本身（防火牆的核心功能是核心層處理，跟這個管理服務是分開的行程），但管理平面反覆失聯本身就是個嚴重問題——尤其是你正在靠它做故障排查的時候。

## 算總帳：升版淨值是負的

- 想要的功能：升版前就已經被硬體排除，跟版不版本無關
- 加密強度調整：有做到，但這個完全不需要升大版本，舊版一樣做得到
- 新的 DNS 推送機制：還沒調通就先放棄了
- 管理服務穩定性：**這是升版前不存在的全新問題**

唯一站得住腳的實質產出，是一個新 bug。

決定當天就降回舊版。**降版不是點一下按鈕就好**——沒有真正的「回退」操作，只能把設備重置成出廠狀態、重新上傳舊版韌體、再匯入一份對應版本的設定備份。好在我保留了升版前做的加密強度調整（匯入的是降版前臨時做的最新備份，不是升版之前那份舊的），沒有前功盡棄，重做一次的功夫省下來了。

降版後版本確認、三條隧道的設定跟降版前一致，管理介面反應恢復到正常速度，短時間內沒有再觀察到那個死鎖現象。

## 三個帶得走的教訓

**沒有明確要解決的問題，升大版本本身就是風險敞口。** 我這次升版的動機（提早熟悉新功能）聽起來合理，但沒有經過「這個功能我現在真的用得到嗎」這一步查證——如果查證做在升版之前，會直接看到硬體排除，根本不會走到後面這些麻煩。

**退路的真實代價，要在下決定之前算清楚，不是出事之後才發現。** 「大不了降回去」聽起來是句安慰話，但「降版」實際上是完整的重置+重建流程，不是反悔按鈕。

**「現在連得上」不能證明系統健康。** 這次最陰險的地方就是它會自己緩過來——如果我只在某個時間點查一次，看到一切正常就下結論，會完全錯過這是一個會反覆重現的真問題。多次、獨立來源的確認（自己動手驗證，加上另一個人在完全不同的操作路徑上獨立撞到同一個現象），才是站得住腳的證據，而不是「看起來目前沒事」。
