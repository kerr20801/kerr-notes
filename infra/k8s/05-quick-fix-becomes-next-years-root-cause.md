# K8s 事故的真正根因，藏在一年前的一次「先讓它動起來再說」

> **結論先說**：一次成功的緊急修復，代價可能不是「解決了問題」，是「換了一個看不見的、有明確引爆日期的問題」。這篇是 [`2026-08-01-kubelet-cert-auto-rotation-failure.md`](2026-08-01-kubelet-cert-auto-rotation-failure.md) 那次事故的後續深挖——當時只找到「憑證自動輪替沒生效」，沒查出「為什麼」。後來查出來了，答案比原本想的嚴重得多。

---

## 原本以為的故事

kubelet 用來跟 API Server 做身分驗證的憑證過期了，觸發連鎖故障。原本的結論停在這裡：「輪替機制不知道為什麼沒生效，止血修復完成，根因留白」。

止血修復本身沒問題。留白的那部分才是真正的故事。

---

## 真正的故事：一年前的一次「先救活再說」

往回查憑證的簽發時間，發現一件精確到詭異的事——**這張最終過期引爆事故的憑證，簽發時刻剛好是一年前同一支腳本執行的時間點**。不是巧合，是同一支腳本、一年前那次執行，就已經埋下了這次事故。

拼湊時間軸：

1. **一年前**：kubelet 服務出了狀況（原因已不可考），有人用最快的方式讓它活過來——把管理員憑證直接複製過去取代 kubelet 自己的憑證檔案。
2. **這個動作立刻有效**。kubelet 起來了，服務恢復，事件結案。
3. **但這個動作同時做了兩件沒人注意到的事**：
   - kubelet 原本會在憑證效期走到七八成時自動換發新憑證，換上去的憑證是寫死的，輪替機制形同被拔線，不會再自己更新。
   - 換上去的憑證身分不是 kubelet 原本該有的「這台節點」權限，是管理員權限。
4. **那張管理員憑證本身有一年效期**——所以「一年後的今天」不是巧合，是那個修復動作當下就已經寫定的引爆時間。

一次成功的急救，變成一顆定時炸彈，只是引信剛好長達 365 天，長到沒人會把兩件事聯想在一起。

---

## 更嚴重的部分：沒人發現權限被放大了

比「憑證會過期」更嚴重的，是過期之前的那一整年。

正常情況下，一個節點的 kubelet 只該有「管理這台節點」的權限。換上管理員憑證之後，這台節點的 kubelet **用叢集管理員的身分運作了一整年**，完全沒人發現。

這代表：那一整年裡，只要這台節點被攻破，攻擊者拿到的不是「一台 worker 的控制權」，是「整個叢集的控制權」。這已經不是可用性問題，是貨真價實的安全問題，而且潛伏期長達一年——因為修復當下沒人有理由去檢查「憑證換上去之後，權限範圍有沒有跟著變」。

```
正常故事：緊急修復 → 問題解決 → 結案
真實故事：緊急修復 → 問題「看起來」解決 → 安全機制被關掉 → 權限被放大
          → 潛伏一年（沒人知道）→ 憑證到期 → 舊問題以新面貌重演
```

---

## 為什麼這件事潛伏了一整年沒被發現

再往下查，發現讓它藏得住的不是運氣，是監控本身有兩個洞：

**健康檢查查錯了對象。** 停掉 kubelet 不會讓已經在跑的容器消失（容器是獨立進程，不依賴 kubelet 存活），所以「叢集看起來還有 API 在回應」這件事，跟「kubelet 本身是否健康」完全是兩回事。健康檢查如果查的是前者，kubelet 真死了也測不出來。

**只在異常時發聲的監控，區分不了「一切正常」跟「監控已經死了」。** 這兩種情況收到的都是「沒有訊息」，同一支排程腳本在另外兩台機器上其實一整年沒有真正成功執行過（環境變數設定的小疏漏），也是因為同樣的沉默設計，沒人發現。

## 這件事更通用的教訓

不是「不要用複製憑證這招急救」，是更根本的東西：

> **任何能讓症狀立刻消失的動作，都要問一句「這個動作除了讓症狀消失，還關掉了什麼我沒注意到的東西」。** 症狀消失不等於問題解決，只代表你手上暫時沒有可以觀察的訊號了——這兩者的差別，往往要等問題換一個樣子回來才會被發現。

配套的第二個教訓：**如果一個修復動作的副作用是「未來某個固定時間點會爆炸」，那個時間點通常就是修復當下用到的東西的有效期**。下次排查一個「莫名其妙一年後才發作」的事故，先問「一年前的今天，是不是有人做了什麼」。

## 一句話版本

> 事故現場找到的根因，往往只是最後一根稻草。真正的根因常常躲在更早、而且看起來已經「處理完畢」的那次操作裡——處理完畢的判斷標準通常只是「症狀消失了」，很少有人回頭確認「消失的方式乾不乾淨」。
