# 機制通了之後：真的搬一整個月資料量會踩到什麼

> 上一篇結束在「新叢集就緒，舊叢集還沒開始正式動手」。這篇接著講：真的開始大量搬遷之後，才會冒出來的那些問題——單一測試、單一台機器測不出來的東西。

---

## 先定範圍，不要一次全上

歸檔層本身涵蓋好幾種資料類型，但決定這一輪只處理其中一種、一個月份的量體，其他的先不碰。不是技術上做不到，是**先把一條完整路徑（含清理、含異常處理）走順，比同時鋪開好幾條半成品路徑更划算**。搬遷腳本设計成可以重複執行、每次只推進一點，用排程反覆呼叫直到全部完成，不是一次跑完的長任務。

---

## 第一個真實 bug：查詢方式選錯，資料量大就爆

搬遷前要先知道「這個資料類型底下有哪些天的 index」。第一版做法是用列出詳細清單的 API——結果資料量一大，這支 API 本身就會逾時，因為它會**無條件收集每個 shard 的完整統計資訊**，即使畫面只要顯示 index 名稱也一樣。

換成另一支專門做「名稱/別名快速解析」的 API 後，同樣的查詢從逾時邊緣（要拉到很誇張的秒數才勉強過）降到不到一秒。**同一個問題（列出符合條件的 index），選錯 API 會差兩個數量級的效能**——這種坑只有資料量真的大到一個程度才會現形，小規模測試永遠測不出來。

## 第二個真實 bug：低權限帳號的查詢，會「安靜地」查不到東西

原本負責搬遷操作的帳號是刻意設計的低權限帳號。結果同一支 API 換帳號查，**低權限帳號回傳空結果，不是報錯，是安靜地什麼都沒有**——因為那支 API 本身需要更高的權限，權限不夠時不會噴錯誤訊息，就直接回傳空清單，看起來就像「這個資料類型完全沒有 index」。

排查方式是拿高權限帳號同一支 API 對照著查，才發現落差。**API 回傳空結果不代表資料不存在，可能是查詢帳號權限不夠又沒有報錯**——這類「安靜失敗」比明確報錯更難抓，因為表面上一切正常。

---

## 快照倉庫是單執行緒的，沒人告訴你

搬遷機制是「打快照、還原、確認筆數對齊、刪來源」四步。跑到一定並發量後，開始出現快照刪除操作反覆逾時，重試好幾次（甚至拉長到分鐘等級的逾時）都還是失敗。一開始以為是程式邏輯有問題，後來查快照倉庫本身的狀態端點才發現真相：

**同一個快照倉庫，任何時刻只允許一個快照操作（不管是建立還是刪除）在執行**，這是底層系統本身的設計，不是我們程式碼的問題。設定了同時處理四個 index 的並發上限，實際到了倉庫這一層全部要排隊——當某個 index 的快照建立卡在收尾階段（可能耗時二十分鐘以上），這段時間內任何刪除請求都只能在後面等，逾時長短完全取決於當下排在前面的操作還要多久,不是把逾時數字調大就能解決的。

**這解釋了整個「快照操作逾時」現象的本質：不是偶爾卡住，是持續在排隊，只是隊伍長度隨時間變化。**確認這件事之後，處理方式從「盲目重試」變成「先查倉庫狀態端點，看是不是真的有排隊，是的話單純等待，不是的話才需要真的介入排查」。

---

## 「清乾淨」這件事本身需要防丟失設計

搬遷成功後，舊資料快照理論上要順手清掉，不然歸檔層的儲存空間會被中繼檔案佔滿。第一版設計是「index 搬完就不會再被程式碰」，結果撞到一次真實案例：來源刪除成功、緊接著要刪快照時，因為前面講的排隊問題連續逾時，這個快照就永久孤兒了——不會出現在任何一輪的待處理清單裡，因為 index 本身已經標記完成，沒有機制會再回頭清理它。

修法是**独立一份「這個 index 完成後緊接著要清掉快照」的追蹤清單**，一旦來源刪除成功就立刻記進去（在嘗試刪快照之前就先存檔，確保萬一中斷也不會漏），之後每一輪都會重試清單裡所有項目，直到真的成功才移除。**善後動作要跟主流程分開追蹤，不能假設它一定會跟著主流程一起完成**——這個設計後來也真的救回過一次程式本身逾時中斷的情況，下一輪自動重試就補上了。

---

## 還原到最後幾個檔案，會卡在「看起來沒動」很久

還原進度到 99% 之後，卡在同一個檔案數字（例如 319 個檔案還原了 318 個）超過一小時沒有變化，一度以為是卡死。實際查還原狀態的詳細端點才發現：**還在動，只是最後一兩個檔案特別大，在儲存資源緊繃的情況下爬得極慢**，不是真的卡住。這類狀況判斷方式很簡單——查還原詳細進度，看已還原的位元組數字是不是還在緩慢往上爬，而不是只看百分比或檔案數字這種粗顆粒度指標。

---

## 快照失敗有好幾種原因，但處理邏輯可以共用

跑了夠多輪之後，快照失敗的原因慢慢分成幾類：

- 單純節點層級的內部錯誤（`aborted`）
- 節點在快照過程中短暫離開叢集又自己歸隊（`node left the cluster`）
- 資源壓力導致的長時間無回應（後面會細講）

發現到第二類原因時一開始有點緊張，直覺是「是不是真的有節點掛了」。查證流程是：先確認叢集當前的節點總數是否跟預期一致、有沒有真的少一台——確認都在，代表是暫時性抖動，用跟第一類完全一樣的清理流程處理即可（刪快照、從追蹤清單移除、重跑）。**不用因為錯誤訊息字面上聽起來比較嚴重，就自動升級處理方式**，先查證再決定。

還撞過一個更隱蔽的變形：清理完重跑之後，還原階段報「同名 index 已存在」。查證發現是前一次失敗的還原嘗試，在目的端留下一個空殼 index（有名字、沒資料、查詢會回錯誤而不是空結果），沒被自動清掉、擋住新的還原。而且這個問題**不是只有前面提到的快照失敗場景才會發生**——後來確認過一次完全正常的快照、正常觸發還原，結果照樣撞到「已存在」，研判是還原觸發的請求本身在網路層逾時/中斷，但目的端其實已經開始建立空殼 index。修法很直接：確認來源端資料還在（代表真正的刪除步驟還沒執行過，安全）、確認目的端是空殼（查得到名字但查不到資料筆數），兩個條件都符合就把目的端的空殼刪掉，讓還原重新觸發。

## 大叢集的「假性紅色」跟「真紅色」，要分清楚

搬遷過程監控整體叢集健康時，撞過兩種看起來都是「紅色」（最嚴重等級）的情況，但本質完全不同：

**第一種**：整體狀態顯示最嚴重等級，但細查「真正遺失主要複本」的計數卻是零，矛盾。深挖每個 shard 的狀態才發現，是一批完全跟搬遷無關的其他資料類型的複本，正在因為某個節點短暫離線而重新選出新的主要複本——這個「重新選出」的過程中，那個 shard 短暫處於一個既不算遺失也不算正常運作的中間態，導致整體判定拉到最嚴重等級,但幾分鐘內節點自己歸隊、選舉完成，就恢復正常了。**這種情況不需要任何人工介入，等它自己收斂即可，介入操作反而可能干擾自癒過程。**

**第二種、也是規模最大的一次**：真的有一個節點完全沒回應，查證發現**根本原因是一次長達十分鐘以上的垃圾回收停頓**——這段時間裡，那個節點的程式完全停擺，連自己的心跳訊號都送不出去，被叢集判定「沒回應」而踢出，牽連的資料量遠超單一次操作能觸發的範圍（波及上千個 shard）。**這是典型的「垃圾回收造成的假性故障」——不是硬體壞、不是網路斷，是應用程式自己被停頓卡死到看起來像死掉一樣**，事後那個節點自己重新加入，資料一筆沒少，只是恢復重新分配需要時間。

兩種情況的共同教訓：**看到最嚴重等級的警示，第一件事不是驚慌介入，是先分辨是真的資料遺失風險、還是自癒過程中的正常暫態、還是資源壓力造成的假性故障**——三種原因處理方式完全不同，前兩種等待即可，第三種需要先確認影響範圍再決定要不要暫停手上其他會加重負載的動作。

## 進度沒有等速，但要對「速度會變」有心理準備

搬遷速度整個過程並不穩定——會有連續好幾輪幾乎沒進展，也會有突然一輪內清掉好幾個 index 的加速期。查證後確認這是底層儲存資源在不同時間點的壅塞程度不同造成的，不是機制本身有問題。**面對這種不等速的長任務，合理的應對是拉長檢查間隔（避免頻繁檢查卻總是拿到「沒變化」的空結果），而不是頻繁介入想辦法加速**——除非有具體證據顯示是某個可調整的參數造成的瓶頸。

## 回頭看，這輪學到的東西

- **同一個查詢需求，選錯 API 可能差兩個數量級效能**——「能用」跟「這個規模能用」是兩回事，一定要拿接近真實規模的資料測過
- **低權限帳號的查詢失敗有時候是安靜的空結果，不是報錯**——排查卡關時記得換高權限帳號對照，排除掉是不是權限造成的假性「查無資料」
- **共用資源（快照倉庫）背後常有隱性的序列化限制**，逾時逾長不代表程式有 bug，先查底層狀態端點確認是不是單純排隊
- **善後清理動作要獨立追蹤，不能依賴主流程一定會順利完成**——用一份持久化的「待清理清單」，每輪都重試,直到真的成功才移除
- **進度卡在同一個數字很久，不代表卡死**——查更細顆粒度的進度指標（位元組數而非百分比/檔案數）再下判斷
- **錯誤訊息的原因分類，處理邏輯常常可以共用**——先查證是不是真的異常（節點是否真的消失），再決定要不要升級處理方式
- **整體健康狀態的「最嚴重等級」不等於「資料真的丟了」**——分清楚自癒暫態、假性故障（資源壓力型）、真實故障三種情況，反應方式完全不同
- **長任務的進度不會等速，拉長檢查間隔比頻繁介入更合理**——除非真的找到具體可調整的瓶頸參數
